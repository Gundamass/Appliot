# 稳健控件自动填充设计

## 目标

让投递助手在招聘网站存在自定义日期、下拉框和组合控件时，仍能尽可能自动完成整份表单。用户只在最终审核阶段介入，不因单个字段失败而中断任务。目标是将人工参与量降低约 80%，同时保持禁止最终提交的安全边界。

## 核心策略

- 高置信度字段直接填写并通过读回校验。
- 中等置信度字段允许自动填写，但在最终审核中标记为“建议关注”。
- 低置信度字段不猜测，保留为空并集中进入最终审核清单。
- 单字段失败只记录字段级结果，继续处理后续字段。
- 所有最终结果都必须回到任务审核页，由用户确认后才能结束任务；系统永不执行最终提交。

## 控件识别

浏览器观察层扩展为统一控件模型，支持：

1. 原生 `input`、`textarea`、`select`。
2. ARIA `combobox`、`listbox`、`option` 组件。
3. 常见自定义下拉组件，包括通过可点击容器展开选项的年月控件。

观察结果需要保留控件的逻辑标签、可见选项、当前值、父级上下文和控件类型。两个共享“开始时间”标题但分别显示“年”和“月”的控件，必须规范化为两个字段，并分别映射到同一个日期语义，例如 `work[0].startDate`。

## 日期与选项值

候选人档案中的日期使用规范值，例如 `2026-04-12`。填写前按控件语义投影：

- 年控件只能得到 `2026`。
- 月控件只能得到 `04` 或页面真实选项对应的 `4`。
- 日控件只能得到 `12`。
- 完整日期控件才得到 `2026-04-12`。

执行器不把完整日期字符串直接交给年月子控件。选项显示文本和实际 value 不一致时，先按显示文本选择，再读回实际值；必要时尝试规范化的 `04`、`4`、`2026年`、`2026` 等候选表示。

## 自动恢复与审核分级

每个字段最多经过以下恢复链：

1. 按控件原生 API 或标准 Playwright 操作填写。
2. 重新观察并按当前可见选项匹配等价值。
3. 对自定义控件执行“展开、读取选项、选择、读回”的控件适配流程。
4. 使用标签、父级上下文和日期组件位置进行一次结构化候选匹配。

恢复成功则继续任务；恢复成功但置信度为中等时，将字段标为建议关注。所有恢复方式失败时，将字段标为待补充并继续，不阻塞其他字段。

## 数据流

1. Observer 识别页面控件并生成结构化快照。
2. Semantic Resolver 将控件映射到档案语义。
3. Production Field Resolver 解析档案值，并完成日期组件投影。
4. Controlled Executor 按控件类型执行填写和自动恢复。
5. Readback Validator 记录期望值、实际值、尝试次数、置信度和失败原因。
6. Application Service 汇总全部字段结果，进入最终审核页。

## 错误处理

- 页面刷新或控件消失：重新观察一次后继续当前字段。
- 选项不匹配：尝试规范化候选值；仍不匹配则记录 `option_not_found`。
- 读回不一致：记录 `readback_mismatch`，继续后续字段。
- 站点特殊行为：由站点适配器扩展控件策略，不将站点判断散落在通用执行器中。
- 任何最终提交按钮和提交请求继续由现有安全策略阻断。

## 测试与验收

- 原生 `select` 能正确选择显示文本与 value 不一致的选项。
- 原生日期控件能填写完整日期。
- 自定义年月控件能分别选择年份和月份。
- 完整日期不会被写入年控件或月控件。
- 首次读回失败时能自动恢复，不中断后续字段。
- 中等置信度字段进入最终审核并显示提醒。
- 低置信度字段保持为空并进入待补充清单。
- 真实 DJI/Moka 流程可以完成填写和审核前停留，但不会提交。
