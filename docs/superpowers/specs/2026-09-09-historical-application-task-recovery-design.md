# 历史填写任务恢复快速修复设计

## 问题

历史任务可能把 URL 后面的自然语言编码进最后一个查询参数。例如目标地址中的
`userId=125079440` 被保存成 `userId=125079440这个页面可以投递吗`。浏览器因此打开
错误目标，观察结果为零字段，Runtime 以 `application_page_unrecognized` 失败；任务页仍可能
显示较早的“等待表单”投影，让用户误以为任务一直运行。

## 目标

1. 新建、读取和恢复任务时使用同一套保守 URL 规范化逻辑。
2. 只修剪能够明确判断为误拼到查询参数末尾的中文自然语言，不改写正常 URL、编码路径或合法中文参数。
3. 历史任务首次读取时事务性更新 `application_tasks.application_url`；若存在对应 Runtime 应用状态，同步更新其中的 `applicationUrl`。
4. 已经失败且错误为 `application_page_unrecognized` 的任务提供“修正地址并重新开始”恢复动作，不原地篡改不可逆执行历史。
5. 前端重连或重新加载时，API 返回的 `failed`、`cancelled`、`review_locked` 终态优先于旧 SSE 投影，并显示中文失败原因。

## 数据流

```text
数据库旧任务
  -> 保守规范化 URL
  -> 无变化：原样返回
  -> 有变化：同一事务更新任务 URL 与 Runtime 应用状态
  -> API 返回最新终态和恢复动作
  -> 前端以 API 终态覆盖旧事件投影
```

“重新开始”创建一个基于规范化 URL 的确定性新任务，旧失败任务继续保留用于审计，不删除其事件、
checkpoint 或 TraceSink 记录。

## 错误处理

- URL 无法解析、无法明确识别误拼文本或修剪后不是公共 HTTPS 地址时，不自动更新。
- Runtime 状态与任务 URL 不一致时，不静默启动浏览器；返回明确恢复提示。
- 数据库更新失败时保留原记录并返回稳定错误，不产生半更新状态。

## 测试

- 仓储测试覆盖本次 Wondershare 原始污染 URL、正常中文参数、编码路径和无 URL 文本。
- Runtime 恢复测试覆盖任务表与 Runtime 状态同步。
- API 测试覆盖失败任务的修正地址恢复动作及确定性新任务。
- 前端测试覆盖 API 终态压过旧 SSE 状态、中文失败原因和恢复按钮。
- 对真实历史任务执行只读预检，再在备份后运行迁移与前后端回归。

## 非目标

- 不增加完整 ReAct 意图循环。
- 不扩展 ATS 页面识别规则。
- 不自动提交申请或绕过登录、验证码、最终确认。
