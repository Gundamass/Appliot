# ATS 自动填写稳定化设计

日期：2026-08-14

## 背景

当前自动填写流程已经具备确定性字段映射、语义补全、受控浏览器执行和提交前审核，但真实招聘页面暴露出以下问题：

- “工作经历”和“实习经历”被视为同一重复区块，导致只有实习资料时仍新增空工作经历。
- 搜索型下拉框在页面重新渲染后会生成新的字段 ID，使同一业务字段重复获得重试机会。
- 部分自定义下拉框完成了输入和候选项查找，但没有可靠地提交选中值或完成回读。
- 语义补全缺少严格的栏目边界，可能将语言能力、薪资等字段映射到英文名、微信号、性别或现居住地。
- 二轮语义补全已经存在，但前端仅根据最近一次操作推断阶段，无法展示真实执行状态。
- 候选人档案缺少结构化语言能力，导致招聘页面存在字段而档案无对应资料。

## 目标

1. 在不自动提交申请的前提下，提高国内 ATS 的自动填写覆盖率和准确率。
2. 将用户参与集中在最终审核，无法安全填写的字段保持空白并明确说明原因。
3. 保留 RAG，但将其限制为未知字段的语义路径识别，不允许从整个档案任意挑选值。
4. 让任务进度与后端真实执行流程一一对应。

## 非目标

- 不让系统自动选择岗位或自动提交申请。
- 不迁移或改写现有候选人档案内容。
- 不使用生成内容填充实习描述、项目亮点或缺失的事实资料。
- 不为每个招聘网站重写完整填写流程；仅为复杂控件提供必要的 ATS 适配。

## 总体流程

```text
等待用户进入简历填写页
  -> 识别页面栏目、重复项和字段
  -> 确定性字段映射
  -> 从结构化档案精确取值
  -> 对剩余字段执行栏目内 RAG 语义映射
  -> 从确定的结构化路径精确取值
  -> 值归一化与控件执行
  -> 页面回读验证
  -> 最终人工审核
```

RAG 只回答“页面字段对应哪个档案路径”，不直接回答“应该填写哪个候选人值”。路径确定后，系统必须从该路径精确读取已确认资料。

## 栏目与重复经历

### 工作和实习分流

- 页面栏目必须区分“正式工作经历”和“实习经历”。
- 档案中 `employmentType` 为实习的记录只能进入实习经历。
- 只有 `employmentType` 明确标记为正式、全职或等价类型的记录才能进入正式工作经历。
- `employmentType` 缺失或无法识别的记录不自动归入任一独立栏目，保留为空并进入审核提示。
- 页面将两者合并为“工作/实习经历”时，两类记录可以按档案顺序共同填写。
- 页面分开显示且没有正式工作资料时，不新增工作经历，不复制实习资料。
- 如果正式工作经历为网站必填项，则保留为空并进入审核提示。

### 新增记录规则

- 新增数量由“兼容当前页面栏目的档案记录数”决定。
- 每次点击新增后必须重新观察页面，并确认对应栏目记录数确实增加。
- 不允许为了满足页面结构创建没有资料来源的空记录。
- 不自动删除网站已有记录，避免破坏用户在网页上的手工输入。

## 字段映射与 RAG

### 第一轮：确定性映射

优先使用字段注册表、ATS 已确认字段目录、页面栏目和重复项序号生成结构化路径，例如：

```text
本科专业 -> education[0].major
赛事名称 -> awards[0].name
实习公司 -> work[0].company
```

### 第二轮：受限语义映射

只有第一轮未解析的空字段进入 RAG。候选路径必须同时满足：

- 属于当前页面栏目。
- 与当前重复项类型和序号兼容。
- 控件类型与字段定义兼容。
- 相似度、候选间距和模型置信度达到自动填写阈值。
- 对应结构化路径存在已确认档案值。

语言能力字段只能检索语言能力定义；薪资字段只能检索求职与薪资定义。禁止跨栏目使用英文名、微信号、性别、地址等资料。

### 无资料处理

- 没有结构化资料时保持空白。
- 必填字段进入审核问题，非必填字段记录为“档案无资料”。
- 不通过相似文本、证据片段或模型生成方式编造候选人事实。

## 语言能力档案

候选人档案新增可重复的“语言能力”栏目，每条记录包含：

1. 语言名称
2. 掌握程度
3. 听说能力
4. 读写能力

语言能力记录独立于证书。大学英语四级、六级、雅思等证书和分数继续保存在证书栏目；后续如招聘页面只有综合语言字段，可在明确规则下引用两类资料，但不得自动互相覆盖。

## 搜索控件与时间选择

### 有限重试

- 所有搜索型下拉框最多执行两次，包括学校、专业、城市、公司、语言等控件。
- 重试计数键使用“任务 + 页面栏目 + 重复项序号 + 语义路径 + 控件角色”，不使用会随 DOM 重渲染变化的字段 ID。
- 第一次使用档案原值；只有存在明确、保守的归一化规则时，第二次才能使用归一化值。
- 两次均失败后停止，不再由后续观察轮次重新获得重试机会。

### 值归一化

归一化只处理不会改变事实含义的格式差异，例如去除专业名称末尾的“专业”、统一年月格式和数字前导零。归一化结果仍需命中唯一候选项。

### 选中和回读

- 输入搜索词不等于完成选择。
- 系统必须点击唯一候选项，并等待弹层关闭或选中状态出现。
- 时间控件必须分别选择年、月等组件，不能只输入文本。
- 执行后重新观察控件值；只有页面回读与目标值一致才记为成功。
- 候选项歧义、弹层未关闭或回读不一致均记为失败。

## 真实任务进度

前端采用“紧凑真实进度”方案。

### 状态模型

尚未进入填写页时显示“等待进入简历填写页”。进入表单后，后端显式维护以下阶段：

1. 精确填写
2. 语义补全
3. 回读校验
4. 最终审核

每个阶段都有 `pending`、`running`、`completed`、`skipped`、`failed` 状态。阶段状态由后端持久化并通过任务事件发布，前端不再根据最近一条操作推断。

### 默认视图

默认只显示：

- 当前阶段及各阶段状态。
- 当前字段和操作，例如“正在选择：本科专业”。
- 当前尝试次数，例如“尝试 1/2”。
- 精确命中、RAG 命中、用户已有值、未匹配和执行失败数量。

点击“查看填写明细”后，再按栏目展示字段路径、填写来源、执行结果和未填写原因。RAG 没有候选字段时显示“已跳过”，不会伪装成完成补全。

## 安全与错误处理

- 终端提交按钮继续由策略层禁止执行。
- 用户在受控浏览器中的操作优先，检测到冲突时暂停自动化。
- 搜索失败和语义未解析默认采用继续处理其他字段的策略，不让单字段阻塞整个任务。
- 页面结构变化、目标字段消失或回读结构不一致时停止当前字段，并记录稳定、可展示的原因码。
- 最终审核必须列出未填写和失败字段，不将失败字段计入已完成。

## 测试方案

### 单元测试

- 正式工作与实习记录分流。
- 未知用工类型不会被默认归入正式工作或实习栏目。
- 合并工作/实习栏目兼容两类记录。
- 重试计数不受 DOM 字段 ID 变化影响，第三次调用被拒绝。
- 栏目受限语义映射禁止语言与基本信息、薪资与地址之间的跨域命中。
- 语言能力字段注册、完整度和档案编辑行为。
- 阶段状态、统计数量和当前动作由后端事件正确产生。

### 浏览器集成测试

- 只有一条实习时不新增正式工作经历。
- 搜索型专业、学校等控件最多执行两次。
- 自定义下拉框必须点击候选项并通过回读。
- 年月控件分别选中且页面值保持稳定。
- 无语言资料时不填写语言栏目；有语言资料时按四个字段精确填写。
- 第一轮完成后，剩余字段真实进入受限 RAG 阶段。

### 真实页面回归

使用国内 ATS 的真实页面进行受控回归，记录页面栏目、字段覆盖、失败原因和截图。测试始终停留在最终提交前，不执行提交操作。

## 验收标准

- 只有实习资料时，正式工作栏目不产生系统新增的空记录。
- 用工类型未知时不会自动创建正式工作或实习记录。
- 任一搜索型控件在一个任务内最多尝试两次。
- 所有下拉框成功状态均有点击和回读证据。
- 无语言资料时语言字段不再出现跨栏目错填。
- RAG 命中能够在进度与字段明细中单独统计。
- 进度阶段与后端真实状态一致，失败和未匹配不会计入完成数。
- 整个流程仍然不会自动提交申请。
