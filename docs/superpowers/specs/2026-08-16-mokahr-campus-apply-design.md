# Mokahr Campus Apply 岗位页适配设计

## 背景

岗位匹配入口已经接受 `mokahr.com` 及子域名，但用户打开
`https://app.mokahr.com/campus_apply/<tenant>/<campaign>#/jobs` 时，浏览器观察器无法把页面识别为岗位列表。观察器返回 `unknown`，通用 Moka 适配器继而返回 `unsupported_job_entry`，前端便错误地提示为“不支持 Moka/Mokahr”。

问题不在域名白名单，而在 `campus_apply` 单页应用的岗位列表、岗位详情和申请页面没有被结构化观察器覆盖。修复必须适配该模板系列，不能把任一租户名称写入代码。

## 目标与边界

目标是支持 `app.mokahr.com/campus_apply/<tenant>/<campaign>` 的三种安全入口：岗位列表、岗位详情和简历申请表单。岗位列表需能提取所有可见、可导航的岗位；岗位详情需能提取单个岗位及正文；申请页继续分流给现有直接投递流程。

本增量不访问真实招聘网站、不绕过登录或验证码、不自动选择岗位，也不改变最终提交的双重禁止策略。挑战页、登录页、iframe 或 Shadow DOM 边界、以及无法建立可靠岗位身份或跳转地址的页面，仍必须返回 `unknown` 或既有挑战诊断，不能猜测成功。

## 方案

采用“专用 Mokahr `campus_apply` 模板识别 + 现有通用观察器兜底”。`JobObserver` 仍只产出通用 `JobPageSnapshot`；Moka Job Adapter 仍负责 URL 归属、页面入口确认和把快照转换为岗位领域对象。这样不会将 ATS 规则扩散到 API、匹配或前端层。

### 页面识别

观察脚本先识别路径是否满足 `mokahr.com` 域下的 `/campus_apply/<tenant>/<campaign>` 模板。满足时按以下有序规则产生 `entryHint`：

1. 出现简历上传、候选人信息等既有申请表单信号时，标为 `application_form`。
2. 出现可见、可导航的岗位卡片集合时，标为 `job_list`。
3. 出现单个岗位的标题、职责或任职要求正文，并能建立岗位身份与申请/返回列表导航时，标为 `job_detail`。
4. 否则保留现有登录检测与 `unknown`；不因 URL 本身把页面猜成岗位列表。

专用分支会覆盖 Moka 常见的岗位元素形态：带岗位 ID 数据属性的项、包含岗位详情哈希链接的锚点、以及以 `position`、`job`、`recruit`、`post` 等稳定语义类名标记的可点击列表项。只有标题和可用的规范链接都存在时才产出卡片；链接按当前页面 URL 解析且必须留在 Moka/Mokahr 域中。若页面把岗位 ID 藏在不可导航的纯点击控件中，本版本拒绝将其伪造成可投递链接。

普通 `social-recruitment`、Synthetic ATS 和其他站点继续使用现有通用选择器与识别逻辑，避免回归。

### 结构化抽取

Mokahr `campus_apply` 专用卡片抽取顺序为：显式岗位 ID、详情链接/URL、卡片标题、组织、地点、摘要。抽取会做 NFKC 标准化、可见性检查、父卡片去重、规范 URL 去重和上限截断。组织名称缺失时沿用通用观察器的 `Unknown` 占位；地点和摘要继续是可选字段。

岗位详情同样以一张结构化卡片表示：优先使用页面中的岗位 ID 和当前 URL，标题来自岗位标题元素，正文来自详情容器中的职责、任职要求和福利等可见文本。正文保留在 `visibleText` 的既有边界内，后续由现有 Adapter 提取硬性条件与技能，不引入额外模型或内容猜测。

筛选读取、映射和翻页保持原有 `FilterPlan` 协议。专用分支额外支持 Mokahr 常见的 `data-*` 筛选属性及现有通用属性；不能可靠定位的筛选控件应当由 Adapter 标为 `localOnly`，而不是宣称已写入网站。分页只点击已识别的下一页控件，点击后继续使用既有读回观察。

### 失败与安全行为

- `ChallengeDetector` 优先级不变；检测到挑战或交互式边界时，Adapter 仍拒绝页面。
- 登录、空加载态、无可导航岗位的列表、或 URL/DOM 结构不符合模板时均返回 `unknown`，使 API 继续产生稳定的可恢复错误。
- 不改变 `JobMatchService` 的会话、租约、排序、用户选岗和转投递逻辑；页面仅在形成可信快照后才进入这些阶段。
- 前端沿用 `unsupported_job_entry` 的错误路径，但文案改为准确说明“当前页面结构尚未识别”，不再把浏览器观察失败泛化为“不支持 Moka/Mokahr”。

## 测试与验收

实现严格按 TDD 进行。先在 `apps/browser-worker/src/job-observer.test.ts` 增加可复现的 `campus_apply` 快照测试并观察其失败，再实现最小的专用分支。测试覆盖：

1. `campus_apply` 岗位列表中可导航岗位卡片被识别、规范化、去重并标记为 `job_list`。
2. 岗位详情被识别为 `job_detail`，且能产出单一可信岗位卡片和正文。
3. 简历申请页优先识别为 `application_form`，不会误判成岗位详情。
4. 登录页、挑战页、不可导航的伪岗位卡片和未知结构保持拒绝。
5. 筛选读回和分页沿用现有协议，既有通用岗位页测试不回归。
6. `moka-job-adapter` 继续接受 `campus_apply` 产生的列表和详情快照，并拒绝跨域或不完整链接。
7. API 创建会话的定向回归确认：可信列表可创建并进入会话；未知结构仍返回 `unsupported_job_entry`；全过程不创建投递任务、不提交页面。

完成前运行 Browser Worker 与 Moka Adapter 定向测试、岗位匹配 API 定向测试、工作区全量测试、类型检查和构建。真实站点仅可做人工只读验证，必须停在用户审核边界，且不得读取或记录用户简历、登录态或页面中的个人隐私数据。

## 完成标准

- 同一实现覆盖任意租户的合法 `campus_apply` 模板链接，不含公司名称特判。
- 可信岗位列表、岗位详情和申请页进入正确分流；不可信页面安全拒绝。
- 岗位卡片始终拥有同域、可导航的规范链接，后续用户选择后可进入既有投递流程。
- 原有 Moka、Mokahr、DJI 和 Synthetic ATS 岗位匹配测试保持通过。
- 整个流程不会自动选岗、创建未确认的投递任务或触发最终提交。
