# 审查后稳定化修复设计

## 目标与范围

本轮修复上一轮代码审查清单中第 3 项之后的功能与安全问题，并执行完整系统回归。范围包括：

1. 补齐 PDF 简历结构化抽取字段并严格校验模型返回的字段路径。
2. 升级存在高风险漏洞的生产依赖，并修复升级造成的兼容问题。
3. 让候选人档案更新可靠地同步到活动投递任务，服务重启后也能继续同步，并让同步失败对用户可见。

本轮明确不实现本地档案、PDF 和头像加密，也不调整敏感资料发送至 DeepSeek 或向量服务的策略。这两项保留为后续独立安全任务。

## PDF 抽取字段契约

结构化抽取不再维护一条容易遗漏的手写字段字符串。系统从候选人字段注册表导出模型可抽取的规范路径模板，并将模板用于提示词和输出校验。数组路径统一使用非负整数下标，禁止未知根字段、未知叶字段、负数或非整数下标。

抽取范围在现有基础上补齐：

- `awards[index]`：名称、时间、级别、描述。
- `campus[index]`：组织、角色、起止时间、描述和成果。
- `publications[index]`：标题、类型、出版方、日期、作者、链接和描述。
- 字段注册表中允许由 PDF 提取的其他档案叶字段。

DeepSeek 返回任一非法路径时，结构化响应校验失败并进入 Provider 的既有重试或升级模型流程，非法事实不会写入数据库。证据原文、页码与置信度校验保持不变。

## 生产依赖升级

对 `pnpm audit --prod` 报告中的直接依赖执行最小兼容升级，优先处理 Fastify、Drizzle ORM、React Router 及其传递依赖。升级遵循以下规则：

- 不改变现有 API 路由、前端地址和数据格式。
- 不以 `overrides` 强行覆盖存在 API 不兼容风险的核心依赖。
- 每次升级一个依赖族，先运行该模块测试，再运行全量测试。
- 若审计项没有可用修复版本，则记录漏洞、可利用条件和现有缓解措施，不能误报为已修复。

目标为消除所有有可用修复版本的高危生产漏洞，并确保没有新增高危漏洞。

## 档案热同步

候选人档案每次成功新增、修改、确认或删除事实后，数据库中的档案修订号递增。活动投递任务记录最后应用的档案修订号，刷新过程具备幂等性：同一修订只应用一次，较旧刷新不得覆盖较新结果。

同步协调器不只刷新内存中的 actor。它从持久化任务仓库查找尚未结束且允许继续填写的任务，恢复所需 actor 后重新匹配仍为空的字段。页面已有非空值和用户手动输入继续保持不覆盖。

档案保存与任务同步分为两个结果：

- 档案持久化失败时，保存请求失败。
- 档案保存成功但投递同步失败时，保存请求仍返回成功，同时返回同步状态并写入任务事件。前端显示“档案已保存，投递同步失败，可重试”，而不是静默忽略。

同步失败不得使任务进入提交状态，也不得触发最终提交动作。用户可以手动重试同步，服务恢复后也可根据未应用的修订继续处理。

## 兼容与迁移

数据库新增修订元数据时使用幂等迁移：旧数据库启动后获得初始修订号，既有任务的最后应用修订按零处理，从而在首次恢复时进行一次安全刷新。迁移失败则拒绝启动，避免部分 schema 生效。

接口新增字段采用向后兼容方式：现有前端所需字段不删除、不改名；新增同步状态由更新后的前端消费。测试中的内存依赖提供等价默认实现。

## 验收标准

- PDF 中的获奖、校园、论文等信息可抽取为独立、合法且有证据的档案事实。
- DeepSeek 返回未知字段路径时不会写入档案，并按既有模型失败策略处理。
- 生产依赖审计不再包含有可用升级路径的高危漏洞。
- 保存档案后，当前活动任务仅重新匹配空字段，页面已有值不被覆盖。
- API 或 Browser Worker 重启后，未结束任务仍可接收尚未应用的档案修订。
- 同步失败在 API、任务事件和前端均可见，并能重试。
- PDF 导入、档案编辑、精确填充、二轮 RAG、重复经历、下拉框、任务取消与删除、最终审核流程通过回归。
- 自动化命令和代码路径均不具备招聘申请最终提交能力，真实页面测试停在用户审核前。
- API、Browser Worker、Web、E2E、类型检查、生产构建、依赖审计和 `git diff --check` 均执行并记录结果。

## 实施顺序

1. 以失败测试固定字段路径白名单和新增抽取字段行为，再实现统一字段契约。
2. 分依赖族升级并运行局部及全量回归，处理兼容性变化。
3. 以失败测试固定档案修订、任务恢复、同步错误可见和重试行为，再实现持久化同步协调器。
4. 执行完整自动化回归，并在可控条件下验证本地真实投递流程始终停在最终审核前。
