# 投递任务列表删除设计

## 背景

当前投递审核列表只有“进入任务”入口，用户必须打开详情页才能删除任务。对于重复任务、失败任务和不再需要处理的任务，这会增加不必要的操作成本。

## 目标

在任务列表卡片上直接删除任务。删除活动任务时，先取消受控浏览器流程，再删除本地任务记录；任何删除操作都必须经过确认。

## 交互设计

每张任务卡片保留“进入任务”作为主操作，并新增带垃圾桶图标的“删除任务”按钮。按钮提供可访问名称和悬浮提示。

点击删除后：

- 活动状态（登录等待、补充资料、内容审核、填写、校验、导航等）：确认框说明“将先取消受控浏览器操作，再删除任务记录”。
- 终态（已取消、失败、审核锁定）：确认框说明“删除后仅移除本地任务记录”。
- 用户取消确认：不调用 API。
- 用户确认：活动任务先调用允许的取消命令，再调用删除接口；终态任务直接调用删除接口。

删除期间当前卡片的删除按钮禁用，避免重复请求。成功后从列表中移除；失败时保留卡片并显示错误。

## API 与状态边界

复用现有 `ApplicationApi.command(taskId, { type: "cancel" })` 和 `ApplicationApi.delete(taskId)`。前端只在任务命令列表包含 `cancel` 时发送取消命令，以兼容已经终止或审核锁定的任务。

后端删除接口继续执行现有状态校验：任务必须处于 `review_locked`、`cancelled` 或 `failed`。活动任务通过取消命令进入 `cancelled` 后再删除，不改变“提交前人工审核”的安全边界。

## 错误处理

- 取消失败：停止后续删除，卡片保留并提示取消失败。
- 删除失败：卡片保留并提示删除失败。
- 删除成功：从当前列表移除，不强制跳转详情页。

## 测试范围

- 列表仅渲染需要人工处理的任务，并为每张卡片提供删除按钮。
- 终态任务确认后直接删除，不调用取消。
- 活动任务确认后先取消再删除，且成功后触发列表移除回调。
- 用户取消确认时不调用任何 API。
- 删除失败时任务仍保留并显示错误。
