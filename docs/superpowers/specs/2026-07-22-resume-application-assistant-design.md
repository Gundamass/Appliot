# 简历投递助手设计规格

- 日期：2026-07-22
- 状态：设计已确认，等待书面规格复核
- 产品形态：单用户本地 Web 应用 + 本地受控浏览器自动化服务
- 核心原则：自动填写和推进中间页面，但永不代替用户提交申请

## 1. 背景与目标

用户向本地应用上传 PDF 简历，系统提取并整理个人信息，形成可编辑、可验证、可追溯的个人资料库。用户提供企业招聘页面 URL 后，系统启动持久化浏览器会话，由用户手动完成登录、验证码和多因素认证。系统随后识别招聘表单，检索个人资料，自动填写普通字段，并在页面校验通过后自动保存草稿或进入下一页。

当系统缺少资料、字段语义不明确、证据冲突或需要生成岗位相关内容时，系统暂停并向用户追问或请求审核。到达最终投递页面后，自动化进入锁定状态，最终提交只能由用户在真实浏览器中亲自执行。

### 1.1 产品目标

1. 从 PDF 简历提取结构化信息，并保留每条信息的原文证据和页码。
2. 提供完整资料编辑页面，使结构化资料成为后续投递的唯一事实来源。
3. 实现有规划、有检索、有验证、有追问、有修正的 RAG 闭环。
4. 支持通用 ATS 表单识别，并通过站点适配器增强常见 ATS 的稳定性。
5. 自动填写普通字段，自动保存草稿，并自动推进多页中间流程。
6. 基于岗位描述微调简历已有的自我评价，并在填写前展示给用户审核。
7. 在工具和执行层禁止最终提交，而不是只依赖模型提示词。
8. 在应用或浏览器异常后，从安全检查点恢复投递任务。

### 1.2 非目标

MVP 不包含以下内容：

- 多用户、账号注册、多租户隔离和云端同步。
- 批量投递、无人值守投递或自动寻找岗位。
- 自动绕过验证码、短信验证、扫码登录或 MFA。
- 保存或自动填写招聘网站密码。
- 自动生成简历中没有证据支持的经历、技能、证书或资格。
- 自动点击最终的提交、确认投递、发送申请或等价终局动作。
- Workday 专用适配器、投递数据分析和自动简历版本推荐。

## 2. 已确认的关键决策

1. 产品首先服务用户本人，全部核心数据和浏览器会话保留在本机。
2. 产品采用结构化语义工作流，不采用可任意点击网页的自由浏览器 Agent。
3. 通用表单语义识别是基础能力，Moka 和北森是首批增强适配器。
4. PDF 是资料初始化入口，经过确认的结构化资料是投递时的事实来源。
5. 中间的保存草稿和下一步操作可以自动执行，但前提是当前页已完成回读和校验。
6. 自我评价可以结合岗位描述微调，但必须显示原文、微调稿、修改理由和证据，并由用户确认后才能填写。
7. 岗位专属回答默认只属于当前任务，不会污染长期个人资料。
8. 最终提交能力不会暴露给 Agent；到达终局页面后自动化进入 `review_locked` 状态。

## 3. 总体架构

系统分为六个职责独立的模块。

### 3.1 本地 Web 应用

负责 PDF 上传、个人资料确认和修正、投递任务创建、聚合追问、内容审核、任务进度和最终审核。Web 应用只访问本机 API，不直接读取浏览器 Cookie，不直接控制浏览器，也不保存招聘网站密码。

### 3.2 任务协调器

任务协调器维护投递状态机，协调页面解析、RAG、策略审批和浏览器执行。它不直接产生个人事实，也不具备任意网页操作能力。

```text
created
  -> waiting_for_browser
  -> waiting_for_login
  -> observing_page
  -> planning_retrieval
  -> waiting_for_answers | waiting_for_content_review
  -> filling_page
  -> validating_page
  -> navigating_intermediate
  -> observing_page
  -> review_locked
  -> user_submitted | user_cancelled
```

`user_submitted` 只表示系统观察到用户手动提交后的成功状态，不代表系统执行过提交。

### 3.3 个人资料与 RAG 服务

负责 PDF 解析、资料结构化、证据存储、混合检索、答案验证、追问生成和修正回写。所有输出必须包含候选值、证据、置信度、适用范围和处理状态。

### 3.4 表单语义引擎

负责将不同招聘网站的 DOM 和无障碍信息转换为统一的表单中间表示。通用解析器处理标准 HTML 表单；Moka 和北森适配器处理各自的动态组件、重复经历、级联选择和日期控件。

### 3.5 动作策略层

负责审批每一个会改变网页状态的自动化动作。模型只能提出结构化动作建议，策略层决定是否允许执行。终局操作和含义不明的高风险操作不能进入执行器。

### 3.6 受控浏览器执行器

负责启动或连接持久化 Chromium 会话，读取页面、执行已批准的结构化动作、回读字段值和收集页面校验错误。执行器不调用模型，不访问完整个人资料库，只接收完成当前动作所需的最小数据。

### 3.7 建议技术结构

MVP 使用 TypeScript 单仓库，减少本地部署时的运行时数量：

- Web：React + Vite。
- 本地 API 和任务协调器：Node.js + Fastify。
- 浏览器执行器：独立 Node.js 进程 + Playwright。
- 数据库：SQLite；结构化查询使用普通索引，关键词检索使用 FTS5。
- 小规模向量检索：向量存入 SQLite，由应用层执行余弦相似度计算。个人简历语料很小，MVP 无需引入独立向量数据库。
- PDF 文本提取：`pdfjs-dist`。
- OCR 回退：本地 Tesseract worker，支持中文和英文页面。
- 模型接口：可替换的 OpenAI-compatible provider adapter。
- 进程间契约：共享 TypeScript schema，并在运行时校验所有跨进程消息。

建议的代码边界：

```text
apps/web
apps/api
apps/browser-worker
packages/contracts
packages/profile-domain
packages/rag
packages/form-semantics
packages/action-policy
packages/site-adapters
```

## 4. 数据模型

### 4.1 个人资料

个人资料至少包含基本信息、教育、工作、项目、技能、语言、证书、链接、基础自我评价和长期求职偏好。

每条事实保存以下元数据：

```json
{
  "field_path": "work_experience[0].company",
  "value": "某科技公司",
  "status": "user_confirmed",
  "confidence": 0.98,
  "scope": "profile",
  "source": {
    "document_id": "document-id",
    "page": 2,
    "text": "2022.07 - 2024.08 某科技公司..."
  },
  "revision": 3
}
```

事实状态为：

- `extracted`：由系统从 PDF 提取，等待用户确认。
- `user_confirmed`：用户确认，可用于普通字段自动填写。
- `user_corrected`：用户修正，优先级高于原 PDF 提取值。
- `superseded`：被新版本替代，仅保留用于审计。

### 4.2 岗位和投递任务

每个投递任务独立保存公司、岗位、招聘 URL、岗位描述、浏览器会话引用、当前状态、检查点、字段计划、检索结果、实际填写值、校验结果、任务专属回答、自我评价微调稿、策略拒绝记录和最终审核摘要。

任务专属资料默认不会写回个人资料。用户可以明确将某项回答设为长期默认值。

### 4.3 证据和索引

系统同时保存三种表示：

1. 结构化事实，用于姓名、电话、日期等精确字段。
2. PDF 原始片段和页码，用于证据展示和事实验证。
3. 关键词及语义索引，用于项目、自我评价和技能等长文本检索。

向量永远不是唯一事实来源。任何自动填写值都必须能追溯到已确认结构化字段、PDF 证据或当前任务中用户已确认的回答。

## 5. PDF 入库流程

1. 计算文件指纹，避免同一 PDF 被重复导入。
2. 按页提取文本，并保留页码、段落位置和原文。
3. 对没有有效文本的页面执行 OCR，并标记其来源为 OCR。
4. 模型依据固定 schema 提取候选事实，必须同时返回支持该事实的原文片段。
5. 执行确定性验证，包括邮箱、电话、URL、日期格式和经历时间逻辑。
6. 检测重复值和冲突，例如同一经历出现不同结束时间。
7. 在个人资料页展示待确认事实和原文证据。
8. 用户确认或修正后，事实才升级为可自动填写状态。
9. 更新 FTS 和语义索引，并记录资料版本。

如果文本提取和 OCR 都失败，系统保留原文件并引导用户手动录入，不生成无证据事实。

## 6. RAG 闭环

### 6.1 规划

表单语义引擎识别字段后，RAG planner 为每个字段确定规范字段语义、所需事实类型、检索范围、是否需要岗位描述、是否允许自动填写、是否属于敏感承诺，以及需要执行的验证器。

### 6.2 检索

- 精确字段直接读取已确认结构化资料。
- 经历类字段读取对应实体并附带原始证据。
- 长文本先用关键词缩小范围，再用语义相似度排序。
- 技能声明同时检索支持该技能的项目或工作经历。
- 自我评价同时检索基础自评、岗位要求和相关经历证据。
- 薪资、入职时间、出差意愿等任务问题优先读取本任务答案，其次读取用户明确设置的长期默认值。

当前任务中的用户确认值只在本任务内具有最高优先级。其后依次使用个人资料中的 `user_corrected` 和 `user_confirmed` 值。仅提取但未确认的值只用于追问和资料审核，不能成为自动填写候选。

### 6.3 验证

验证值是否有证据支持，字段类型、长度、格式和选项是否匹配，日期和经历是否冲突，以及生成文本是否引入没有证据的新技能、经历、证书、数字或承诺。写入网页后，还必须验证页面回读值与计划值一致。

字段结果状态为：

- `verified_auto`：证据和格式充分，可以自动填写。
- `needs_review`：存在合理候选值，但必须由用户确认。
- `needs_question`：资料不足、冲突或字段语义不明确。
- `blocked`：风险过高、验证失败或动作不允许执行。

### 6.4 追问

系统按当前页面汇总所有 `needs_question` 字段，一次性向用户提问。问题必须说明页面原文、系统理解、缺少的信息和答案适用范围。

### 6.5 修正

系统记录修正前后的值、用户原始回答、适用范围、对应字段、任务和资料版本。只有用户明确选择“保存为长期资料”时，任务答案才会更新个人资料库；更新后重建相关索引。

## 7. 自我评价微调

```text
基础自我评价
  + 当前岗位描述
  + 已确认的相关项目和技能证据
  -> 生成岗位微调草稿
  -> 事实覆盖和新增声明检查
  -> 展示原文、草稿、修改理由和证据
  -> 用户编辑或确认
  -> 写入当前任务
```

微调只调整强调顺序和措辞，不能创造新经历。没有证据支持的技能、年限、成果数字和资格必须删除或标记。未经用户确认，草稿不能写入招聘页面；确认后默认只属于当前任务。

## 8. 表单语义和填写流程

### 8.1 表单中间表示

每次进入新页面，浏览器执行器生成结构化快照：

```json
{
  "page": {
    "url": "https://example.com/application",
    "title": "填写个人信息",
    "stage": "application_form"
  },
  "fields": [
    {
      "id": "field_12",
      "label": "最高学历",
      "type": "select",
      "required": true,
      "options": ["本科", "硕士", "博士"],
      "current_value": ""
    }
  ],
  "actions": [
    {
      "id": "action_3",
      "text": "下一步",
      "classification": "intermediate_navigation"
    }
  ]
}
```

页面快照只暴露不透明的字段和动作 ID。模型不能使用坐标点击或向 Playwright 发送任意脚本。

### 8.2 识别层级

1. 读取 HTML 标签、无障碍名称、关联标签、选项、必填状态和浏览器校验规则。
2. 如果命中已知 ATS，使用适配器补充动态组件、重复经历、日期控件和级联选择。
3. 只有含义仍不明确时，模型才结合附近文字和页面上下文判断字段语义。

### 8.3 每页执行循环

```text
解析当前表单
  -> 映射个人资料字段
  -> RAG 检索和验证
  -> 汇总缺失问题
  -> 用户回答或审核生成内容
  -> 生成结构化填写计划
  -> 动作策略审批
  -> 执行填写
  -> 触发 input/change/blur
  -> 回读字段和页面错误
  -> 自动保存或进入下一页
```

执行器检查必填字段、页面错误、实际值、动态新增字段和重复经历是否保存成功。重新定位或重填只允许有限次数；超过限制后任务暂停并显示失败字段。

## 9. 动作策略和禁止提交

### 9.1 动作分类

| 类别 | 示例 | 策略 |
| --- | --- | --- |
| `safe_edit` | 输入、选择、上传简历 | 自动允许 |
| `intermediate_save` | 保存草稿 | 当前页校验后自动允许 |
| `intermediate_navigation` | 下一步、继续填写 | 当前页校验后自动允许 |
| `unknown_side_effect` | 含义不清的确认、发送验证码 | 暂停并询问用户 |
| `terminal_submit` | 提交申请、确认投递、完成申请 | 永久禁止自动执行 |

### 9.2 强制安全边界

1. Agent 工具接口不存在最终提交方法。
2. 模型只能引用表单快照中的字段或动作 ID，不能任意点击、运行 JavaScript 或调用浏览器网络接口。
3. 所有网页写操作必须经过动作策略层；浏览器执行器拒绝缺少有效策略审批的命令。
4. 策略层结合按钮文案、DOM 属性、周边提示、当前阶段和表单上下文识别终局动作。
5. `terminal_submit` 永不生成可执行令牌；无法确定含义的终局页面动作按阻止处理。
6. 到达最终页面后，任务进入 `review_locked`，自动化停止接受点击类命令。
7. 用户在真实浏览器中亲自审核和提交。系统可以观察成功页，但不能触发提交。

该边界保证即使模型受提示注入、误判按钮或输出错误动作，也无法绕过策略层完成提交。

### 9.3 登录和验证

用户在持久化浏览器中手动完成用户名、密码、验证码、扫码和 MFA。系统只检测登录状态，不读取或保存明文密码，不尝试绕过任何验证机制。

## 10. 用户体验

### 10.1 个人资料页

按基本信息、教育、工作、项目、技能、证书、链接、自我评价和偏好组织资料。每条资料显示确认状态，并允许查看 PDF 页码和原文证据。

### 10.2 新建投递页

用户输入招聘页面 URL，选择简历，并可确认系统获取的岗位描述。系统启动浏览器后，引导用户在浏览器中手动登录并进入申请页。

### 10.3 投递任务页

展示公司、岗位、当前页面、任务状态、浏览器连接状态、已完成页数和当前 Agent 动作。普通字段自动处理；待回答问题按页面集中展示。

### 10.4 内容审核页

用于审核低置信度答案和自我评价微调。自我评价并列展示原文、微调稿、修改理由和证据。用户可以采用、编辑后采用或继续使用原文。

### 10.5 最终审核页

展示全部已填写字段、来源、临时回答、自我评价变更、页面错误、未确认项和策略警告。应用不提供提交按钮，只提供切换到真实浏览器进行人工审核的命令。

## 11. 检查点、异常和恢复

系统在页面解析、用户回答、内容确认、字段填写和页面跳转后创建本地检查点。恢复时必须重新观察当前网页，并把新快照与检查点比较，不能盲目重放旧操作。

- PDF 文本提取失败：尝试 OCR；仍失败则保留文件并要求手动录入。
- 登录、验证码或 MFA：暂停并等待用户。
- 页面结构变化：重新生成快照和字段映射。
- 元素失效：重新定位一次，仍失败则暂停。
- 页面校验错误：读取错误文本，修正格式并有限重试。
- 模型或网络不可用：保留检查点，稍后继续。
- 未知动作：默认阻止并询问用户。
- 意外域名跳转或第三方授权弹窗：暂停并提示用户检查。
- 恢复时已位于最终页：直接进入 `review_locked`。

本地审计日志保存页面快照摘要、检索证据、填写计划、实际结果、策略决定、失败原因和用户修正。日志不得保存密码、Cookie、验证码或无关页面敏感内容。

## 12. 本地数据与模型隐私

- PDF 原文件、结构化资料、索引、任务记录和浏览器用户目录保留在本机。
- API key 存入操作系统凭据存储，不写入 SQLite、日志或源码配置。
- 调用云端模型时，只发送当前字段所需的最小证据片段和岗位上下文。
- Cookie、密码、验证码、完整浏览器存储和无关页面内容不得发送给模型。
- 模型 provider 必须可替换，后续可以接入本地模型而不改变 RAG 和浏览器契约。
- 浏览器执行器和模型调用模块分进程隔离，执行器不能自行向模型传输页面数据。

## 13. MVP 范围与迭代顺序

MVP 包含文本型 PDF 解析、扫描页 OCR 回退、带证据和版本的资料库、完整 RAG 闭环、通用表单识别、Moka/北森适配器、单个持久化 Chromium 会话、自动填写和中间推进、自我评价审核、最终审核锁、检查点和审计日志。

建议分三段实现：

1. 个人资料、PDF 入库、证据模型和 RAG 闭环。
2. 通用表单中间表示、受控执行器、动作策略和模拟 ATS 端到端流程。
3. Moka/北森适配器、最终审核体验、恢复能力和安全测试矩阵。

## 14. 测试策略

### 14.1 单元测试

覆盖资料 schema、PDF 结构化、字段规范化、检索排序、证据验证、任务作用域、动作分类和状态机转换。

### 14.2 表单样本测试

使用固定 HTML fixtures 覆盖文本输入、单选、多选、下拉框、日期、级联选择、文件上传、重复经历、动态字段、页面校验和不同终局按钮文案。

### 14.3 端到端测试

使用 Playwright 和本地模拟 ATS 覆盖手动登录等待、多页自动填写、聚合追问、自我评价审核、页面刷新、浏览器重启、任务恢复和最终审核锁。

### 14.4 安全测试

使用“提交申请”“确认投递”“发送申请”“完成”“立即申请”、图标按钮、动态文案、弹窗、iframe、提示注入和模型恶意动作请求，验证自动化不能提交。所有安全测试都必须证明命令在策略层或执行器边界被拒绝，而不只是模型选择了不点击。

## 15. MVP 验收标准

1. 上传 PDF 后可以生成可编辑、带页码和原文证据的个人资料。
2. 未经用户确认的提取值不能用于普通字段自动填写。
3. 用户修正资料后，相同字段优先使用修正值，并能查看修正历史。
4. 普通字段可自动填写，且页面回读值与计划一致。
5. 缺失或冲突资料会触发明确追问，不会凭空生成事实。
6. 任务专属回答默认不会更新长期个人资料。
7. 自我评价微调会展示原文、草稿、理由和证据，未经确认不能写入网页。
8. 当前页校验通过后，系统可以自动保存草稿和进入下一页。
9. 页面刷新、应用重启或浏览器重启后，可以从检查点重新观察并恢复任务。
10. 未知或高风险动作默认被阻止。
11. 在所有安全测试中，Agent 和执行器都不能执行最终提交。
12. 到达最终页面后，系统展示完整审核信息，最终提交只能由用户在真实浏览器中亲自完成。

## 16. 不可变约束

后续实现计划必须保持：

1. 模型不能直接控制浏览器。
2. 未验证事实不能自动填写。
3. 生成或微调内容必须先由用户审核。
4. 中间页面可以自动推进。
5. 最终提交必须由用户亲自执行。
