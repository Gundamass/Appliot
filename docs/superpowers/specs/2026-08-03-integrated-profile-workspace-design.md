# 档案与投递统一工作区设计

## 目标

将根路径从独立的资料库页面升级为唯一的“档案与投递”工作区。候选人先在完整长表单中确认和补全长期资料，再从同一页面创建投递任务；系统先完成确定性填写，再仅对剩余空字段执行受约束的语义映射，最后停在人工审核边界，绝不自动提交。

## 路由与入口

- `/?view=profile`：默认视图，候选人档案中心。
- `/?view=apply`：同一工作区内的新建投递入口。
- `/?view=reviews`：仅显示存在待处理事项的投递任务，名称为“投递审核”。
- `/applications/:taskId`：保留具体任务工作台，用于实时浏览器状态、字段追问、内容审核和最终人工检查。
- `/applications/new`：保留兼容路由，跳转到 `/?view=apply`；不再维护独立的新建投递页面。

根路径不是额外的首页，而是候选人档案本身。顶部视图切换只改变工作区内的聚焦区域，不创建第二套档案数据源。
缺少 `view` 或使用未知 `view` 时统一回退到 `profile`。

## 候选人档案

档案由字段注册表驱动，并在页面中呈现完整长表单。每个字段显示来源与确认状态：`已从 PDF 识别`、`已确认`、`用户已修改`、`待补充`、`已加密保存`。用户确认或修改过的值优先于新 PDF 提取结果；发生冲突时只展示差异，不自动覆盖。

首批栏目：

- 基本信息：姓名、邮箱、电话、所在地及需要受保护的身份信息。
- 求职意向：目标岗位、期望城市、实习/就业类型、期望薪资、到岗时间、出差意愿。
- 教育经历：学校、学历、专业、起止时间、成绩、排名、主修课程。
- 实习与工作：公司、岗位、起止时间、职责和成果、用工类型。
- 项目经历：项目名称、起止时间、描述、技术栈、项目要点。
- 技能、证书、获奖经历、论文/专著、链接和附件。
- 自我评价：保存原文；仅在具体投递中可以生成岗位微调建议，且必须经用户审核。

教育、实习/工作、项目和获奖经历均是稳定的可重复记录，不以页面数组位置作为长期身份。普通实习描述和项目要点不由模型生成或重写。

### 获奖经历

获奖经历独立于证书和其他经历。每条记录包含：

- `awards[].name`：获奖名称。
- `awards[].date`：获奖时间。
- `awards[].level`：国家级、省级、市级、校级、院级、企业/协会或其他。
- `awards[].description`：奖项描述。
- 证据来源或附件关联。

字段映射必须在同一条获奖经历的上下文内完成，不能把不同奖项的名称、时间和级别交叉组合。

## 投递前检查与映射

新建投递时，系统读取招聘页面当前字段，并以候选人档案作为唯一长期资料来源。

1. 只处理可见、可编辑且当前为空的字段；官网已有值绝不覆盖。
2. 第一阶段使用字段注册表的精确标签、别名、区块和重复经历上下文确定标准路径，并从档案精确读取已确认值。
3. 第一阶段结束后重新观察页面。
4. 仅对仍为空的合格字段执行第二阶段语义映射。映射必须同时满足相似度阈值、第一二候选差距、字段类型、栏目、选项与风险约束。
5. 字段路径确定后只精确读取档案值，不对结构化值再次做向量检索。
6. 每次自动填写都必须通过页面回读验证；动态字段出现后按既有轮次上限重新观察。

缺失候选资料不阻止其余安全字段填写。系统应以可理解的方式指出缺失：官网字段、档案状态和对应的档案栏目。用户在档案中补充后，任务只重试此前未填写的字段，不重新解析 PDF，也不重复处理已经确认填写的字段。

低置信度、存在冲突、敏感承诺、控制页面结构或没有已确认档案值的字段保持为空，聚合进入“投递审核”。

## 投递审核

“投递审核”是某次招聘投递的人机交接区，不是候选人档案审核。它只展示需要用户判断的事项：

- 未映射或缺少资料的必填字段。
- 语义映射候选不唯一或置信度不足的字段。
- 自我评价的岗位微调建议。
- 需要用户操作浏览器后重新读取的字段。
- 网站特有追问、格式转换或敏感承诺。

每个事项展示官网标签、控件类型、系统理解、候选档案值、来源证据和页面回读状态。用户可补充、修改、确认或拒绝。具体任务仍在 `/applications/:taskId` 中实时更新；根路径的“投递审核”只提供待处理任务入口和数量摘要。

最终提交、投递、确认申请及语义等价动作始终由浏览器 Worker 拦截。系统没有自动提交按钮、命令或恢复路径。

## 视觉与交互

采用工作台风格：左侧紧凑导航或移动端横向导航，主区冷白与浅灰分层。已确认和可安全继续使用低饱和青绿色；待补充和审核事项使用琥珀色；错误使用红色。避免营销式大标题、渐变、嵌套卡片和冗长事件流。

档案首页突出三类信息：档案完整度、可直接填写字段数量、建议补全数量。主区同时展示栏目完整度和当前栏目表单；新建投递视图展示投递前检查与招聘链接输入；投递审核视图只展示有待处理事项的任务。

桌面端与 320px 移动端均不得有文本遮挡、横向溢出或状态变化导致的布局跳动。

## 组件边界

- `ProfileApplicationWorkspace`：根路径工作区，负责解析 `view`、共享导航与视图切换。
- `CandidateProfileCenter`：长表单、栏目导航、完整度、PDF 证据与字段编辑。
- `ApplicationStartPanel`：投递前检查、链接输入、创建任务及进行中任务冲突恢复。
- `ApplicationReviewInbox`：待处理任务摘要和到具体任务页的入口。
- `ApplicationTaskPage`：保持现有实时任务页职责，不成为第二个档案中心。
- `ProfileCompletenessService`：基于字段注册表与已确认档案事实计算栏目与字段缺失情况。

这些组件通过既有 `ProfileApi`、`ApplicationApi` 和任务事件契约通信；档案编辑与应用任务的状态不互相复制。

## 测试与验收

- 根路径默认显示候选人档案；视图切换与 URL 参数可恢复。
- 旧 `/applications/new` 正确重定向至新建投递视图。
- 档案完整度正确计入获奖经历等独立重复栏目。
- 用户可新增和编辑缺失档案字段；已确认或修正值不会被新 PDF 自动覆盖。
- 创建任务前能展示会影响填写的缺失资料。
- 补全资料后只重新尝试任务中仍未填写的字段。
- 精确映射优先于语义映射，低置信度映射不自动填写。
- 档案、投递和审核视图在桌面与移动宽度下无重叠或横向溢出。
- 端到端测试继续断言招聘页面提交计数为零。

## 分阶段实施

1. 统一根路径工作区和路由：将候选人档案、新建投递与投递审核收进同一壳层，保留具体任务页和旧链接重定向。此阶段不改变既有 PDF 提取与投递执行逻辑。
2. 完整候选人档案：扩展字段注册表、可重复经历、独立获奖经历、缺失资料新增/编辑接口和完整度计算。此阶段让长期档案能承载招聘官网常见字段。
3. 投递前检查与增量重试：将网页剩余空字段和档案缺失项关联；用户补全后只重试未填写字段，并复用现有确定性优先、语义兜底和最终审核边界。

每个阶段都必须保持提交计数为零，并分别通过单元测试、组件测试和针对合成 ATS 的端到端回归后再进入下一阶段。

## 非目标

- 不自动生成或改写项目要点、实习描述。
- 不将敏感明文发送至模型、向量库或活动日志。
- 不增加自动提交能力。
- 不为根路径视图引入第二套候选人资料存储。
