# 对话内岗位匹配设计

日期：2026-09-02  
状态：待用户复核  
分支：`fix/mokahr-campus-apply`

## 1. 目标

取消面向用户的独立岗位匹配页面，把岗位匹配完整融入对话：真实执行阶段显示为当前用户轮次下的流程点，匹配结果显示为助手消息中的岗位卡片，筛选、选岗和创建受控投递任务都在对话内继续。

本次只改变交互入口和展示方式，不重写岗位匹配领域逻辑，不削弱确认、人工接管和最终提交锁。

## 2. 已确认体验

用户从对话提出“帮我投递一下百度校园招聘”后，系统按以下顺序工作：

1. 当前用户消息下显示理解请求、Tavily 搜索、URL 校验和等待招聘入口确认等流程点。
2. 用户确认招聘入口和开始岗位推荐后，新用户轮次显示筛选准备、受控浏览器读取和岗位匹配等真实流程点。
3. 需要确认筛选条件时，助手消息直接展示精简的筛选摘要和确认操作。
4. 匹配完成后，助手消息直接展示岗位卡片，不再出现“打开岗位匹配”按钮。
5. 用户可在岗位卡片内查看详情、选择岗位、继续筛选或重新匹配。
6. 选择岗位后，系统仍需在创建受控投递任务前再次确认；不会自动执行最终提交。

流程点保持无卡片的时间线样式，岗位结果使用独立岗位卡片，从视觉上区分“系统正在做什么”和“系统找到了什么”。

## 3. 方案比较

### 方案 A：对话内实时投影，复用现有岗位匹配服务（采用）

聊天消息保存岗位匹配会话 ID，Web 在消息内读取现有岗位匹配 API 的实时状态，并将筛选、结果和动作渲染为对话组件。岗位匹配状态机、版本保护、幂等键和浏览器所有权继续由现有服务负责；对话服务负责为动作创建用户轮次和可审计流程点。

优点：领域逻辑只有一个事实来源，刷新后可恢复，现有安全边界和测试可以复用。缺点：需要把现有工作台的交互拆成适合对话的组件，并补充岗位匹配会话与对话轮次的关联。

### 方案 B：把完整岗位结果复制进对话消息

每次状态变化都生成一条包含完整筛选条件、岗位详情和匹配证据的助手消息。

优点：消息历史完全静态。缺点：会复制大量数据，结果更新和过期状态容易与岗位匹配会话不一致，版本冲突与幂等处理更复杂。因此不采用。

### 方案 C：直接把现有 `JobMatchWorkbench` 嵌入聊天气泡

保留工作台组件，只改变它的挂载位置。

优点：实现速度快。缺点：三栏工作台在聊天消息和移动端中密度过高，视觉上仍像“页面嵌页面”，与已确认的流程点加岗位卡片结构不一致。因此不采用。

## 4. 架构边界

### 4.1 岗位匹配服务仍是状态事实来源

继续使用现有岗位匹配会话和状态机，包括：

- `awaiting_filter_confirmation`
- `extracting_jobs`
- `matching_jobs`
- `awaiting_job_selection`
- `selected`
- `awaiting_login`
- `awaiting_challenge`
- `paused`

岗位读取、评分、证据、差距、冲突、结果过期、重匹配、暂停和继续逻辑不迁移到 React 组件或对话文本中。

### 4.2 对话是交互编排层

对话层负责：

- 将岗位匹配会话关联到创建它的 `conversationId` 和用户 `turnSequence`。
- 把用户点击“确认筛选”“选择岗位”“仍然选择冲突岗位”“继续读取”“重新匹配”等动作记录为新的用户消息。
- 在每个动作轮次下记录真实工具调用和公开执行摘要。
- 在助手消息中挂载一个轻量的岗位匹配会话卡片引用，而不是复制完整领域状态。

### 4.3 Web 是实时投影层

Web 根据消息中的 `sessionId` 使用现有岗位匹配读取接口和 `useJobMatchSession` 获取最新状态。组件只提交严格定义的动作，不从文案重建岗位 ID、结果 ID、版本号或数据库主键。

## 5. 对话内组件

### 5.1 `ConversationJobMatchFlow`

替代现有 `JobMatchSessionCard` 的“打开岗位匹配”按钮，按会话状态选择以下一种内联投影：

- 筛选确认摘要
- 读取中状态
- 岗位卡片列表
- 登录或验证码人工接管提示
- 暂停、失败或结果过期提示
- 已选岗位摘要

它不使用独立页面标题、工作台外壳或多栏布局。

### 5.2 `ConversationJobFilters`

在 `awaiting_filter_confirmation` 状态显示：

- 目标岗位、地点、用工类型等已确认条件。
- 哪些条件映射为网站筛选，哪些条件仅做本地判断。
- “确认筛选并读取岗位”主按钮。
- “调整筛选条件”次操作，发送一条自然语言式用户轮次并在对话中展开可编辑字段。

筛选条件不能为空；岗位期望仍使用现有候选人资料与确认状态。

### 5.3 `ConversationJobCards`

匹配完成后展示岗位卡片。桌面端最多两列，窄屏单列。每张卡片显示：

- 岗位名称、地点和来源。
- 匹配分和置信度。
- 满足、未知、冲突数量。
- 一条最重要的匹配依据或差距摘要。
- “查看详情”和“加入投递清单”操作。

默认先展示满足条件的岗位，再展示存在明确冲突的岗位。冲突岗位不会被静默隐藏，但使用明确的冲突标识和二次确认。

“查看详情”在当前助手消息内展开证据和差距，不跳转页面，不创建嵌套卡片，也不遮挡其他消息。

### 5.4 结果级动作

- 普通岗位：选择后记录用户消息“选择岗位：{岗位名称}”。
- 冲突岗位：先展示冲突摘要，用户明确确认后才选择。
- 过期岗位：禁用选择，提供“重新匹配”。
- 已选岗位：卡片显示已选择，并由后续助手消息询问是否创建受控投递任务。
- 创建投递任务：继续使用现有确认和受控投递流程；最终提交仍被锁定。

## 6. 流程点设计

岗位匹配相关动作必须归属于触发它的用户轮次。建议的公开步骤如下：

| 用户动作 | 流程点 |
| --- | --- |
| 开始岗位推荐 | 理解请求、准备筛选条件、读取招聘页面、等待筛选确认、生成回复 |
| 确认筛选 | 处理确认、应用网站筛选、读取岗位列表、匹配岗位、生成回复 |
| 继续读取 | 理解请求、继续读取岗位、更新匹配结果、生成回复 |
| 重新匹配 | 理解请求、读取最新资料、重新匹配岗位、生成回复 |
| 选择岗位 | 处理选岗、校验岗位版本、保存选择、等待投递确认、生成回复 |
| 创建投递任务 | 处理确认、创建受控投递任务、生成回复 |

只显示真实执行的工具步骤。浏览器未启动时不得显示“受控浏览器”；匹配服务未执行时不得显示“岗位匹配”。流程摘要继续使用白名单脱敏，不显示密钥、Cookie、完整简历、表单值、原始 MCP 报文、DOM、模型提示词或隐藏思维链。

长时间的岗位读取必须持续更新同一个稳定 `stepId`，而不是不断追加重复步骤。暂停、等待登录、验证码接管和失败均使用明确的 `waiting` 或 `failed` 状态。

## 7. 数据与接口

### 7.1 保留现有数据

保留岗位匹配会话、岗位发布记录、匹配结果、选择结果、版本号、执行 epoch、浏览器所有权和应用任务关联。不得把这些数据迁移到对话消息表。

### 7.2 对话卡片

现有 `job_match_session` 卡片继续作为消息中的稳定引用，至少包含：

- `sessionId`
- 招聘入口标题、公司和 URL 的安全显示信息
- 创建该会话的状态摘要

Web 使用 `sessionId` 获取最新投影。推荐岗位继续使用真实 `resultId` 和 `postingId`，不从岗位标题匹配记录。

### 7.3 对话动作接口

新增严格枚举的对话岗位匹配动作入口，输入包含：

- `conversationId`
- `sessionId`
- `action`
- 当前 `sessionVersion`
- 动作所需的 `resultId`、幂等键或确认标志

允许的动作限于：确认筛选、调整筛选、暂停、继续、重新匹配、选择普通岗位、确认选择冲突岗位。服务端验证会话属于当前对话上下文，并调用现有岗位匹配服务。客户端不能直接伪造 assistant 消息或过程事件。

### 7.4 旧地址兼容

移除产品内所有“打开岗位匹配”导航和独立岗位匹配入口。旧的岗位匹配 URL 不再渲染工作台，改为跳转到对话首页，并通过 `sessionId` 恢复其所属会话；无法解析所属会话时进入最近会话并显示“该岗位匹配记录无法在当前对话中恢复”，不得回退到旧页面。

## 8. 状态展示

| 会话状态 | 对话内表现 |
| --- | --- |
| `awaiting_filter_confirmation` | 筛选摘要和确认按钮 |
| `extracting_jobs` | 当前轮次流程点展开，助手卡片显示读取进度和暂停操作 |
| `matching_jobs` | 流程点显示岗位匹配，卡片显示正在整理结果 |
| `awaiting_job_selection` | 岗位卡片列表和筛选/继续操作 |
| `selected` | 已选岗位摘要和创建受控投递任务确认 |
| `awaiting_login` | 等待登录流程点和人工接管入口 |
| `awaiting_challenge` | 验证码或挑战提示，等待人工处理 |
| `paused` | 已暂停说明和继续读取操作 |
| 结果过期 | 原卡片保留但禁用选择，提供重新匹配 |
| 失败 | 公开失败摘要和可执行的重试或调整筛选动作 |

## 9. 错误和恢复

- 页面刷新：消息、流程点和 `sessionId` 从持久化数据恢复；岗位卡片重新读取最新会话状态。
- SSE 断开：保留最后一次投影，显示连接状态；重连后按事件 ID 重放。
- 岗位页面变化：显示“岗位结果已变化”，禁用旧结果选择并提供重新匹配。
- 无岗位结果：不显示空白卡片，助手回复说明未找到满足条件的岗位，并提供调整筛选和继续读取。
- 登录或验证码：暂停自动执行，显示人工接管，不把挑战当作失败或自动绕过。
- 版本冲突：重新读取会话状态，不重复执行用户动作。
- 创建投递任务失败：保留已选岗位，显示可重试错误，不自动提交。

## 10. 响应式与可访问性

- 流程点使用语义列表，折叠按钮具有 `aria-expanded`。
- 岗位卡片使用文章结构，操作使用真实按钮；选中状态不只依赖颜色。
- 桌面端岗位卡片最多两列，390px 及以下单列。
- 岗位名称、最长地点和失败摘要不得溢出或遮挡相邻内容。
- 窄屏可隐藏耗时，但不得隐藏流程标题、失败原因、岗位冲突或关键操作。
- 不新增独立页面级滚动容器，继续使用对话主区域滚动。

## 11. 测试策略

### 契约和 API

- 对话岗位匹配动作的严格输入、版本号、真实 ID 和幂等测试。
- 会话不属于当前对话时拒绝动作。
- 确认筛选、读取、匹配、选岗、冲突确认和创建投递任务的逐轮流程事件顺序。
- 事件摘要脱敏和失败隔离。
- 刷新后恢复会话卡片和流程点。

### Web

- `job_match_session` 卡片不再包含“打开岗位匹配”。
- 各状态映射到正确的内联组件和操作。
- 筛选确认会先插入乐观用户消息，再接收流程事件。
- 岗位卡片普通选择、冲突二次确认、过期禁用和详情展开。
- 两个岗位匹配轮次的流程点不会串线。
- 旧 URL 跳转到所属对话，不渲染 `JobMatchWorkbench`。

### 回归和视觉检查

- 保留现有岗位匹配状态机、适配器、评分、受控浏览器和应用安全测试。
- 对话链路验证招聘入口确认、筛选确认、岗位卡片、选择岗位和投递确认。
- 1280px 和 390px 截图检查：无水平溢出、无卡片嵌套、无独立工作台、流程点与岗位卡片视觉区分清晰。

## 12. 明确不做

- 不删除岗位匹配领域服务、数据库记录或状态机。
- 不把岗位匹配逻辑交给前端或模型自由生成。
- 不根据岗位标题重建岗位 ID 或结果 ID。
- 不自动选择岗位、绕过冲突确认或创建投递任务。
- 不开放最终提交命令。
- 不实现企业招聘状态跟踪、外部状态轮询、Webhook、同步或通知。

## 13. 验收标准

1. 产品内不存在面向用户的独立岗位匹配页面入口。
2. “开始岗位推荐”之后的筛选、读取、匹配、选岗和投递确认均可在对话中完成。
3. 每个用户动作都有归属于该轮次的真实流程点，没有虚构工具调用。
4. 匹配完成后直接显示岗位卡片，不显示“打开岗位匹配”。
5. 刷新后流程点和岗位卡片仍附着于正确消息，并反映最新会话状态。
6. 登录、验证码、冲突岗位、结果过期和失败均有明确且安全的恢复路径。
7. 现有岗位匹配、受控投递、人工接管和最终提交锁保持不变。
8. 390px 视口无水平滚动、文字遮挡或操作丢失。
9. 未实现企业招聘状态跟踪。
