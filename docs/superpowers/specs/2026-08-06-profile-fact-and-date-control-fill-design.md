# 档案事实与日期子控件填写修复设计

## 背景

真实 DJI/Moka 投递任务中，公司名称和职位可以填写，但用户已在候选人档案中保存的工作职责、开始日期和结束日期被留空。运行数据表明问题不在检索召回：相关字段已经精确映射到 `work[0].description`、`work[0].startDate` 和 `work[0].endDate`。

## 根因

1. 候选人档案通过长表单保存时，`user_corrected` 事实的证据文本只记录“用户补充：字段路径”，没有记录实际值。RAG 验证器要求用户证据能够支持候选值，因此这些事实被错误判定为不支持。
2. 招聘网站常把一个日期拆成“年”和“月”两个自定义输入。当前快照丢失了占位符中的子控件信息，两个控件都只保留“开始时间”或“结束时间”，后续无法从完整日期中选择正确分量。

## 方案

### 用户事实证据

- 新保存的候选人档案事实使用验证器已经支持的值证据格式，证据必须包含实际 JSON 值。
- 读取历史 `user_corrected` 事实时，仅兼容系统过去生成的“用户补充：字段路径”格式，将其规范化为与当前事实值一致的用户证据。
- 不信任普通文档证据、不跳过生命周期、作用域、类型、必填项或置信度验证。

### 日期子控件

- 表单快照在主标签相同且控件具有“年/月/日”占位符时，将占位符保留为标签限定信息。
- 条目语义仍映射到规范日期字段，例如 `work[0].startDate`，避免扩展候选人档案数据模型。
- 在字段解析结果通过验证后，根据标签限定信息把 `YYYY-MM-DD` 投影为年、月或日，再生成浏览器填写命令。
- 非日期语义、非标准日期值和没有明确日期分量的控件保持原行为，不猜测。

## 数据流

1. 用户保存档案，仓库写入包含实际值的用户证据。
2. 页面快照识别“开始时间 年”和“开始时间 月”，条目映射均指向 `work[0].startDate`。
3. RAG 精确检索完整日期并完成证据、生命周期和类型验证。
4. 字段适配分别产生 `2026` 和 `04`，Browser Worker 填写后执行原有回读验证。
5. 工作职责直接使用已验证的完整文本，不进行生成或改写。

## 兼容与安全

- 历史证据兼容仅适用于状态为 `user_corrected`、来源为 `user` 且文本严格匹配旧系统格式的事实。
- 不降低语义相似度阈值，不把语义检索结果自动升级为精确匹配。
- 不引入网站域名判断，日期适配对满足同一控件契约的网站通用。
- 最终提交边界不变，系统仍不能执行终态提交。

## 测试

- 仓库测试：新建和更新用户事实的证据包含实际值；历史旧格式事实读取后能够通过值证据验证。
- 表单语义测试：同组“年/月”控件保留分量信息，同时映射到同一个规范日期语义。
- 投递服务测试：完整日期分别投影为年和月，工作职责保持原文并进入填写命令。
- 回归测试：普通文本、原生日期控件、无明确分量的控件和非标准日期值保持原行为。

## 验收标准

- 当前档案中的 `work[0].description`、`work[0].startDate` 和 `work[0].endDate` 能通过验证链。
- 年/月控件接收正确分量，不接收完整日期。
- 教育、项目和工作经历共用同一日期处理逻辑。
- 相关单元测试、API 测试、类型检查和生产构建通过。
