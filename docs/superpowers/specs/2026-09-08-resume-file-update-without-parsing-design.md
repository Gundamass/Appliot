# 简历文件独立更新与旧投递 URL 归一化设计

## 背景

当前 `POST /api/documents` 将 PDF 留存、文本提取、事实提取和档案刷新绑定在一次请求中。用户如果只想替换后续投递使用的简历文件，也会被迫触发 OCR、DeepSeek 和资料事实写入。

同时，URL 意图路由修复只作用于新输入。修复前已经持久化的待确认记录仍可能携带被编码中文污染的 URL；用户稍后确认时，旧 URL 会直接参与确定性任务 ID 计算和浏览器导航。任务 `a0b682fc-7d1d-5b39-b090-1efa4d8bca42` 因此导航到了错误页面，页面分类为 `unknown_page`，未生成填写命令。

## 目标

1. 用户可以只更新当前投递简历，不触发解析，也不修改已有档案资料。
2. 新 PDF 保存成功后立即成为投递文件；是否已解析不影响文件上传。
3. 用户仍可选择“更新并解析”，也可稍后单独重试解析当前文件。
4. 旧上传并解析接口继续可用。
5. 所有任务创建入口在导航和计算确定性 UUID 前再次归一化 URL。
6. 现有数据库、已解析资料和旧任务保持兼容。

## 非目标

- 不自动删除历史 PDF、旧事实或失败任务。
- 不自动合并两个数据库中的测试数据。
- 不改变招聘网站的最终提交确认策略。
- 不为文件更新引入 Agent 或 ReAct 循环。
- 不在本轮重新设计简历事实冲突策略；成功解析沿用现有字段修订语义。

## 核心设计

### 当前简历与解析状态分离

`documents` 表增加 `is_current INTEGER NOT NULL DEFAULT 0`。建立仅允许一条 `is_current = 1` 记录的部分唯一索引。切换当前简历必须在数据库事务中先清除旧标记，再设置新标记。若现有表通过 `CHECK` 约束限制 `import_status`，迁移同时重建该约束以加入 `failed`，不能只修改 TypeScript 联合类型。

现有 `import_status` 保留并明确为解析状态：

- `retained`：文件已保存、尚未解析；
- `importing`：正在解析；
- `completed`：解析完成；
- `failed`：文件仍可用于投递，但上次解析失败。

迁移旧数据库时，如果尚无当前简历，则把最近一条 `completed` 文档设为当前简历。已有文档 ID、指纹、事实证据和源文件路径不变。

文档仓储增加：

- `findCurrent()`：返回当前投递简历，不要求解析完成；
- `setCurrent(fingerprint)`：事务内切换当前文件；
- `claimImport(fingerprint)`：允许从 `retained` 或 `failed` 进入 `importing`；
- `markFailed(fingerprint)`：解析失败时保留文件并记录可重试状态。

用于表单文件字段的解析器改为 `findCurrent()`。依赖已提取文本和证据的流程继续使用已完成文档，不把未解析 PDF 当作可检索证据。

### API 边界

新增以下接口：

1. `POST /api/profile/documents/current`
   - 接收一个 PDF；
   - 校验 MIME、PDF 签名和大小；
   - 计算指纹并通过原文件存储安全留存；
   - 幂等创建或复用文档记录；
   - 将该文档设为当前简历；
   - 不调用 PDF/OCR、DeepSeek 或事实仓储。

2. `POST /api/profile/documents/:documentId/parse`
   - 只允许解析当前简历，避免用户切换文件后旧请求覆盖新状态；
   - 对 `retained`、`failed` 状态加锁进入 `importing`；
   - 成功后原子写入页面、事实和 `completed` 状态；
   - 失败后标记 `failed`，不回滚当前文件，也不修改已有事实；
   - 已是 `completed` 时幂等返回现有解析摘要，不重复调用提取器或模型；
   - 并发请求返回稳定冲突错误。

3. `GET /api/profile/documents/current`
   - 返回当前文件名、文档 ID、解析状态和已提取事实数量；
   - 没有当前文件时返回 `{ document: null }`。

现有 `POST /api/documents` 保留为兼容适配器：先执行“保存并设为当前”，再解析该文档。除“重复内容”由原冲突响应调整为幂等成功外，其余成功响应结构和错误码保持兼容。现有读取已完成文档和证据的接口不变。

同一 PDF 重复上传不是错误：文件已存在时复用记录并将其设为当前。只有内容非法、持久化失败或当前切换失败才拒绝请求。

### 前端交互

“简历解析”面板选择 PDF 后提供两个明确按钮：

- `仅更新简历`：调用当前简历上传接口。成功文案为“当前简历已更新，已有档案资料未改变”。
- `更新并解析`：先上传并切换当前文件，再按返回的文档 ID 调用解析接口。

面板始终展示当前文件名和状态：`未解析`、`解析中`、`已解析` 或 `解析失败，可重试`。解析失败时显示“文件已更新，但解析未完成”，并提供“重新解析”按钮。文件更新成功后不刷新或清空事实列表；解析成功后才刷新事实、完整度和当前文档摘要。

上传过程中锁定两个提交按钮。上传完成、解析尚未开始时即清空文件选择器，防止重复提交。若页面上下文或 API 实例发生变化，沿用现有 generation/owner 机制丢弃过期响应。

### 一致性与失败处理

- 原文件留存失败：不创建文档记录、不切换当前简历。
- 数据库记录或当前切换失败：返回持久化错误；仅清理由本次请求新建且尚未被其他记录引用的临时文件。
- 解析失败：当前 PDF 保持可用于投递，旧事实保持原状，状态变为 `failed`。
- 解析成功：页面、事实和状态在同一事务提交；中途失败不产生部分事实。
- 当前文件在解析期间被切换：解析结果提交事务先以 `documentId + is_current = 1 + import_status = importing` 做比较并交换；条件不成立时回滚页面和事实写入，把旧文档恢复为可再次领取的 `retained`，并返回稳定冲突。
- 同一文件重复上传：返回现有文档并确保它是当前简历。

### 旧投递 URL 的二次归一化

在应用任务创建服务的公共入口增加确定性 URL 归一化，覆盖会话确认、推荐卡片和直接 API 创建：

1. 只接受公共 HTTPS URL；
2. 对查询参数中的 ASCII 标识符后缀执行既有“编码自然语言恢复”规则；
3. 保留合法编码中文路径、合法中文查询值、短中文标识符和普通 URL；
4. 多 URL、HTTP URL 或无法安全判断的输入拒绝创建；
5. 使用归一化后的 URL 计算确定性 UUID、持久化并导航。

旧任务 ID 和旧任务记录不迁移、不覆盖。已经失败的污染任务保留审计记录；用户用正确 URL 重试时创建基于干净 URL 的新确定性任务。

## 数据流

### 仅更新简历

`选择 PDF → 校验 → 留存原文件 → 幂等写入 documents → 事务切换 is_current → 返回当前文档摘要`

这条路径不进入提取器、模型提供器或事实仓储。

### 更新并解析

`仅更新简历成功 → 按 documentId 领取解析 → PDF/OCR 提取 → 事实提取与校验 → 事务写入页面和事实 → 标记 completed → 刷新前端档案`

### 创建填写任务

`任一任务创建入口 → 公共 HTTPS 校验 → URL 归一化 → 确定性 UUID → 持久化任务 → 受控浏览器观察与填写`

## 测试与验收

### 数据库与仓储

- 旧数据库迁移后，最近完成文档成为唯一当前简历。
- 切换当前简历保持唯一索引，重复调用幂等。
- `retained` 和 `failed` 可以重试解析，并发领取只有一个成功。
- 现有文档、事实和任务仍可读取。

### API

- 仅更新接口不调用 PDF/OCR、DeepSeek 或事实写入。
- 仅更新后当前文件变化，事实集合与修订号不变。
- 同文件重复上传成功并复用文档。
- 更新并解析成功、失败、并发冲突和重试行为稳定。
- 兼容接口继续完成保存加解析。
- 当前文档摘要正确反映四种解析状态。

### 投递文件解析

- 未解析的当前 PDF 能被表单文件字段解析器选中。
- 历史已解析 PDF 不再覆盖更新后的当前 PDF。
- 证据读取仍只使用已完成解析的文档。

### URL 回归

- 修复前持久化的 `userId=125079440%...这个页面可以投递吗` 在任务创建时归一化为 `userId=125079440`。
- 任务 UUID、数据库 URL 和浏览器导航 URL 均使用同一个干净值。
- 合法编码中文路径和查询值保持不变。
- 多 URL、HTTP URL 和不确定边界不创建任务。

### 前端与真实浏览器

- 两个按钮及其忙碌、成功、失败和重试状态可访问且文案明确。
- “仅更新简历”后档案字段和完整度不变化，当前文件名更新。
- “更新并解析”成功后刷新档案，失败后仍显示新文件为当前简历。
- 使用合成 PDF 和合成 ATS 完成浏览器联调；不点击招聘网站最终提交按钮。

## 发布与回滚

先发布数据库迁移和兼容接口，再发布前端。迁移只增加列、索引和初始当前标记，不删除数据。出现问题时前端可回退到兼容接口；新增列和历史文件保留。发布前继续使用现有数据库备份策略，并在真实数据库副本上执行迁移与读取回归。
